# Syfuse 规则引擎性能基准 — 原始测量记录

# 本文件**故意入库**：它是性能预算的原始证据。README 与 CHANGELOG 里引用的
# 实测数字必须能在这里核对到，否则那些数字就只是口头声明。
#
# 生成方式：tests/perf_rule_engine.sh [规则数] [测量轮数]
# 每次运行会**追加**，不覆盖 —— 保留历史才能看出性能是否在回归。
# 每段都记录了主机与 JVM 版本，因此不同机器的结果可以区分，不会互相污染判断。
#
# 判读注意：
#
#   1) **不要用单轮结果下结论。** 2026-10-13 之前的记录是单轮测量，
#      已作废（保留仅为留痕）：同一机器、同一份代码的单轮 p99 得到
#      0.9651ms 与 1.3183ms，相差 36%，据此先后写下过"达标余量 3.5%"
#      与"超出预算 1.9 倍"两个互相矛盾的结论，两个都站不住。
#      自 2026-10-13T02:57:36Z 起改为：1 轮预热（丢弃）+ 5 轮测量，
#      取逐轮 p99 的**中位数**为结论（提示词第 11 部分："多轮取中位数"）。
#
#   2) **根因不是"未命中 Trie 的那一半"。** 采样中确实有一半请求未命中
#      域名 Trie，但 `FilterEngine.collectCandidates` 对**每个**请求都会把
#      全部线性规则（此处 10000 条）复制成新列表并逐条测试 —— 命中的请求
#      也一样付这个成本。证据：p50 ≈ 0.60~0.68ms，与 p99 同量级；
#      若只有未命中的一半走线性路径，p50 应该低得多。
#      因此线性扫描主导的是**整个分布**，不只是尾部。
#
#   3) **偶发越线是真实的。** 10 个测量轮里有 2 轮（1.3077ms / 1.2108ms）
#      越过 1ms 预算，其余 8 轮在 0.6878~0.8150ms。这是非实时桌面 OS 上
#      GC 与调度抖动的正常表现，也是必须看中位数与离散度、而不是看单轮的原因。
#      真机上应重新测量（Android 的 ART/GC 行为与 HotSpot 不同）。
#
#   4) 不要跨机器比较绝对值，只比较同一台机器上的趋势。
#   5) 详见 README「性能预算与实测（第 11 部分）」。
